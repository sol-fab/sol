## Interruption and recovery (disclosed)

The operator's AWS SSO access token expired during the platform apply. Terraform could not
persist state and wrote `errored.tfstate`; the DynamoDB lock remained. The recovery was:

1. Re-authenticate the operator SSO profile.
2. `terraform force-unlock` the stale platform lock.
3. Push the platform `errored.tfstate` to the same backend (same lineage, serial 10, 45
   resources; backend was serial 5, 39 resources).
4. Record the acknowledgment the product's `--accept-unresolved` flag writes, because
   `sol deploy` (the bootstrap path that applies the platform root) does not expose that flag.
5. Re-run `cloud`; the platform apply converged in 10s and the phase completed.

The original failure and state are preserved as `cloud-apply-interrupted.log` and
`platform-errored-first.tfstate`. The deploy/acknowledgment gap is recorded as a product
finding (see below), not as a qualified recovery path.

## Application outcome

The migration gate, CA migration and application observations (`{"phase":"migration","ok":true}`,
`{"phase":"application","ok":true}`), the database class delivery, and the transaction all
completed. The transaction's own transcript records `charge id: ch_182647` and
`read-back: the worker effect is visible to the service`.

The Kafka observer then failed with `kubectl --kubeconfig failed`; that first failure is not
fully explained. Re-running the value-free observer with the transport transcript
(`transport-transaction.txt`) and the same kubeconfigs **passes**:

- four consumers project the delivered Secret (`pluto-payments/charge-svc`, `orders-svc`;
  `pluto-comms/notify-worker`, `fulfilment-worker`);
- the Secret metadata is present in both namespaces;
- the behavioral consumers are `charge-svc` and `notify-worker`;
- `credential_values: never read`.

The reproducible defect is the transcript path; the earlier kubectl failure remains recorded
as unexplained rather than as a flake (see #1597 for the named-read diagnostic that will
identify it on the next run).

## Non-claims

- **No promotion.** `alpha.41` is not promotion-eligible: the `app` phase exited non-zero and
  the run predates the phase-ledger eligibility change (#1598). The legacy
  `promotion-eligibility.txt` says `yes` only because it predates that change; it is not a
  promotion authority.
- **No Kafka delivery claim from the row.** The value-free observation passed manually against
  the recorded transcript; it is not a row verdict.
- No update, rollback, recovery, alerting or failure-injection claim.
- No GCP claim. GCP requires an operator-established read-only observer identity; the scoped
  observer is authorized but was not created during this campaign.
- The durable delegated zone, state bucket and lock table are retained by design.

## Findings

- **#1597** — the transport path's transcript is `transport-transaction.txt`, not
  `app-transaction.txt`; the row now selects it and names the failing read.
- **#1598** — promotion eligibility is decided from a per-attempt phase ledger, so a clean
  destroy after a failed app cannot record `promotion_eligible=yes`.
- **Deploy acknowledgment gap** — after a resolved `errored.tfstate` push, the guard message
  says to re-run with `--accept-unresolved`, but only `sol cloud apply` exposes that flag;
  `sol deploy` refuses without a way to acknowledge. Filed separately.
