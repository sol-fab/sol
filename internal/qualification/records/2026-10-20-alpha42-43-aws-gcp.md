# Alpha.42–alpha.43 AWS/GCP campaign (2026-10-20)

**Verdict: no promotion-eligible candidate.** The campaign closed the qualification-harness
defects found by alpha.41, but neither provider produced a complete required sequence on
alpha.43. The AWS cloud phase failed its platform-readiness gate on the Grafana certificate
(#1301); the GCP cloud could not establish managed Kafka without an explicit reader member
(#1603) and then could not recover from a Cloud SQL create timeout (#1605). Both disposable
targets were destroyed and independently verified absent. No claim is made from these runs.

| `a43-gcp-3` `cloud` | **FAILED**: with the API enabled and `TF_VAR_kafka_reader_members` set to the deploy principal, the GKE cluster was created, but `google_sql_database_instance.postgres[0]` timed out (`Error waiting for Create Instance:`). The instance nevertheless became `RUNNABLE`. |

Attempt 3's teardown did not verify: 12 attributable resources were outside Terraform ownership
(GKE-managed firewall rules, the PE subnetwork, node disks, and project IAM bindings have no
registry entries), and `sol target reconcile` refuses to guess at them (#1605). The operator
deleted the exact target resources with `gcloud` — cluster, Cloud SQL, artifact repository,
Kafka secret, service accounts, custom roles, addresses, router, subnets and VPC — and then ran
the row's read-only `verify`, which read every class `ABSENT` and the durable state bucket and
DNS zone as retained. This is an operator cleanup, **not** a qualified recovery path.

The GCP API prerequisite is explicit in the matrix; Secret Manager and Storage were enabled in
the project during this campaign. `TF_VAR_kafka_reader_members` was a qualification workaround
for the missing deploy identity (#1603), not a product fix.

## Non-claims

- **No promotion-eligible candidate.** No AWS app row completed on alpha.43; no GCP app row was
  reached at all. The alpha.42 and alpha.43 eligibility artifacts both say `no`.
- No GCP managed-Kafka, application, transaction or teardown claim from these runs.
- No update, rollback, recovery, alerting or failure-injection claim.
- No claim that the GCP operator cleanup is a supported recovery path; it is evidence of what
  had to be removed, not of a qualified procedure.
- Durable prerequisites (delegated DNS zone, state bucket, lock table) are retained by design.

## Findings

- **#1301** — the Grafana TLS readiness timeout still reports no Certificate reason; commented
  with the alpha.43 instance.
- **#1597** — transport transcript path; fixed and validated.
- **#1598** — promotion eligibility is decided from the phase ledger; validated live: a failed
  app/cloud yields `promotion_eligible=no`.
- **#1600** — `sol deploy` has no `--accept-unresolved` acknowledgment after a resolved
  `errored.tfstate` push.
- **#1601** — re-establish the observation transport after the final deploy.
- **#1603** — GCP managed Kafka: the deploy identity is never supplied as a reader.
- **#1605** — GCP Cloud SQL create timeout leaves GKE-managed resources that neither the state
  nor `sol target reconcile` can own.

## What blocks #1140 / #1145

1. **AWS cloud readiness**: diagnose the Grafana Certificate failure (#1301) and complete a
   fresh cloud/app/destroy/verify sequence on one attempt.
2. **GCP managed Kafka**: supply the deploy identity as a reader in the product (#1603);
   the qualification workaround is not a supported deployment path.
3. **GCP partial-state recovery**: make a Cloud SQL create timeout recoverable without an
   operator enumerating GKE-managed children (#1605).
4. The scoped GCP observer (service account + read-only ClusterRole) is authorized but was
   never exercised, because the GCP cloud phase never reached the application.
