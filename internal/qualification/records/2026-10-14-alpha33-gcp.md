### Scoped out, not bypassed

  HTTP phase does not perform. Recorded in `alpha-rows.txt` as `not-run`, not as a pass.
- The platform's authenticated Kafka transport, the migration gate and the operator-secret stop
  are **profile-derived** and a profile-less deploy has none of them (#1403). This row does not
  claim them; the AWS verdict establishes them.
- The **populated teardown is not a claim of this row** — the GCP row has no populate step. It was
  established on AWS, where the row populates Sol's repositories before destroying.

### The first-pass rollout race, and why the row expects it

`app-deploy-bootstrap` fails: `fulfilment-worker`'s startup probe is refused because the deploy
applies the workloads before the schema the migrations create exists. The row says so itself —
"a profile-less deploy establishes namespaces and applies workloads with no profile gates
(#1403), so the operator secrets are supplied next" — and continues; `migrate-apply` then
succeeds, and the following `app-deploy` brings the workloads up and waits for them.

This is the same ordering the local golden path hits (#1411) and it has the same cause: without a
gate, nothing stops a workload from being applied before its schema. It is expected here, and this
row's assertions are made after the deploy that follows the migration.

## Window shape (disclosed)

The specimen ran in four deliberate phases — `cloud`, `app`, `destroy`, `verify` — which is this
row's design, not a resumption.

Two things before the specimen:

- **Attempt `2b-a33` aborted before provisioning.** The cluster name was too long: Sol refused to
  derive a 32-character service-account id (`sol-qual-gcp-2b-a33-cert-manager`) against GCP's
  30-character limit and said exactly what to do ("shorten the cluster name to at most 17
  characters"). The pre-teardown inventory confirmed nothing had been created. That is a
  fail-closed check working; the specimen was restarted as `2b-a33b` with a 14-character cluster
  name. One attempt is one specimen, and the row enforces it.
- An `app` invocation from a checkout at `4df26a58` (main, past the tag) was refused by
  `candidate-binding`: "the workspace is at 4df26a58 but the candidate is 3b2d3adb; building it
  would qualify another revision's application as this candidate's". The row requires the
  checkout to be the candidate revision **and clean**, so the specimen ran from a clean `3b2d3adb`
  tree with the candidate's own harness. The harness fixes merged after the tag (#1448) are
  therefore *not* in this run — and were not needed: this row's identity can list cluster-wide,
  so #1446's scoped-list defect does not bite here, and the row has no populate step, so #1447
  does not arise.
