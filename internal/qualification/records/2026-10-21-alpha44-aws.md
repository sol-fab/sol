This is the #1301 diagnostic working: the Certificate's `Ready` and `Issuing`
conditions and the ACME order error, not just `kubectl wait`'s timeout.

5-certificates-per-168h limit for this exact identifier set has been exhausted
by the recent campaigns; the retry is `2026-10-21 13:47:59 UTC`. This is not a
harness failure and no product-code defect is established by this run. The next
AWS attempt must either wait for the reset or use a different Grafana
identifier; that is a product/operator decision, not a harness fix.

## Cadence finding — production LE on every AWS attempt

The AWS row uses production Let's Encrypt; GCP defaults to staging
(`CLUSTER_ISSUER=letsencrypt-staging`). Every AWS attempt against
`grafana.qual-aws.sol-fab.dev` consumes one of production's five certificates
per 168h for the exact identifier set; alpha.41–.44 exhausted it. This is a
design/cadence cost, not a code bug.

The operator adopted the staging/promotion split (#1618). #1619 implements it:
the target declaration defaults AWS to `letsencrypt-staging`, the attempt
identity records `issuer=`/`claim=`, and a continuation preserves the original
attempt's issuer/claim (a different issuer requires a new ATTEMPT). The next
attempt is staging (`issuer=letsencrypt-staging`, `claim=mechanism-only`) and is
not promotion-eligible by construction; a clean staging pass runs the mechanism
end-to-end at zero production LE budget. The production promotion attempt
follows the LE reset at `2026-10-21 13:47:59 UTC`.
