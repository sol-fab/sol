## 4. Friction log

**FRIC-1 — the documented substrate command no longer exists.** `sol local infra up` (named by the
`e2e` skill and by the runbook's own step list) was removed when local deployment was consolidated;
`sol local` now offers `deploy`, `down`, `migrate`, `releases`, `rollback`, `run`. The runbook *body*
already says `sol local deploy` twice, so the runbook contradicts itself, and the generated workspace's
own closing output is the only place that is unambiguously right. A first-time user following the
runbook hits a dead command in the first minute.

**FRIC-2 — a fresh scaffold cannot be deployed without knowledge from outside the workspace.** The
first `sol local deploy` fails:

```
error: comms/notify_worker is missing local secret value(s): POSTGRES_URL.
       Add them to sol/secrets.local/comms/notify_worker.env.
```

The scaffold neither creates `sol/secrets.local/` nor supplies an example, and its README mentions the
directory only in a file listing ("ignored per-unit credentials for local run and deploy"). The local
substrate's canonical value — `postgresql://postgres:dev@localhost:5432/sol_dev` — appears in no
user-facing document; it is derivable only from Sol's internal `platform/local/scripts/ensure-postgres.sh`
and the `e2e` skill's infrastructure table. The user is told *which file* and *which key*, never *which
value*.

**FRIC-3 — the requirement itself is the §10 defect.** The error above is the unconditional local
injection of `POSTGRES_URL` and `SOL_API_KEY` into every unit (`sol_cli_local_run.ml`), which the model
states as a defect against the invariant. `notify_worker` is a Kafka consumer whose only database use is
indirect; it is nonetheless required to carry a database URL locally before the workspace can deploy.

**FRIC-4 — a freshly scaffolded workspace always warns about its image tag.**

```
warning: could not resolve the git commit for the image tag (fatal: not a git repository ...);
         tagging images "dev". Pass --image-tag to choose a tag.
```

A generated workspace is not a git repository, so this warning is the *expected* first experience.

**FRIC-5 — an install timeout hides its cause.** Three Helm installs each reported only
`Error: context deadline exceeded` after their 3-minute `--wait`. Nothing in Sol's output said that the
component pods were stuck pulling images, which was the actual cause; establishing that required
`kubectl describe pod` by hand.

## 5. Findings

**The golden path is blocked in a fresh scaffold, before Sol-specific behaviour is reachable.** This is
independent evidence for the premise behind the local half of the resource-bindings work: a first-time
user cannot reach a running service without supplying values that the workspace never tells them.

**Environment, not product, for the substrate failure.** After the secrets were supplied, k3d created
the cluster and three registries' images stalled inside it: `docker.io` (postgresql, loki),
`registry.k8s.io` (metrics-server), `docker.redpanda.com` (redpanda). All were still pulling after 4–5
minutes; `kube-system` pods never left `ContainerCreating`. From the host, the same pull completes in
under 30 seconds, and DNS resolves correctly inside the k3d node. The blocker is TCP egress from the
k3d container, not Sol — but nothing in Sol's output distinguishes that from a Sol failure (FRIC-5).

## 7. Addendum — the substrate-unblock attempt

The environment blocker was attacked directly, so that steps 4–9 could be reached. **They were not
reached, and the attempt produced a second finding about the intended workaround.**

### `k3d image import` does not work in this environment — it is not a usable fallback

The documented workaround fails, and not for the environment's reason:

```
$ k3d image import -c sol-local docker.redpanda.com/redpandadata/redpanda:v26.1.17
ERRO Failed to get nodes for cluster 'sol-local': ... client version 1.43 is too old.
     Minimum supported API version is 1.44
```

This is the Docker-API incompatibility the runbook already documents as FRIC-017 — Docker Engine 29
removed every API below 1.44 while k3d's client speaks 1.43. `sol local deploy` **bridges it for its own
k3d calls** by pinning `DOCKER_API_VERSION`; a hand-run `k3d` command does not get that bridging.

Exporting `DOCKER_API_VERSION=1.44` fixes the *node lookup* but not the import: k3d then executes the
save inside its own `k3d-sol-local-tools` container, whose bundled Docker client is **also 1.43**, and
it fails the same way:

```
ERRO Failed to import image(s) into cluster 'sol-local': ... Exec process in node
     'k3d-sol-local-tools' failed ... Error response from daemon: client version 1.43 is too old
```

**Verdict for the report's purpose: `k3d image import` is not a reliable workaround here — it does not
work at all without further hacking. Do not reach for it first.** Anyone reproducing this should go
straight to the direct containerd path below, or fix egress.

### What did work, partially: a direct containerd import

`ctr` is available inside the k3d node (k3s bundles it), so images can skip both the registry and
k3d's tools container:

```bash
docker pull <image>                        # on the host, where egress works
docker save <image> | docker exec -i k3d-sol-local-server-0 ctr -n k8s.io images import -
```

This is a **manual, per-image hack**, not a supported path, and it is not resumable: each image is a
separate host pull plus import. With it, `sol local deploy` progressed much further on the next run:

```
Redpanda ok   PostgreSQL ok   Loki ok   Alloy ok   Tempo ok
Grafana FAILED   Prometheus FAILED   (ingress-nginx not attempted)
```

### Why it still did not finish

- **Pull failures were repeated, and each attempt costs ~4 minutes** (a 3-minute Helm `--wait` per
  failing component), so convergence by iteration is slow. The host pulls succeed; the failures were in
  the cluster, and under this per-attempt cost the run did not converge inside a reasonable window.
- **~~Several images cannot be pulled from the host at all.~~ Corrected — see below.** The earlier claim
  about `grafana:13.2.1-distroless` was wrong.

Final cluster state before teardown: `grafana` `ImagePullBackOff`, `prometheus-server` `ErrImagePull`,
`alloy` `ImagePullBackOff`.

### Correction: the Grafana image exists and pulls fine

An earlier version of this addendum asserted that `docker.io/grafana/grafana:13.2.1-distroless` "cannot
be pulled from the host at all — where egress otherwise works". **That was wrong, and the two clauses did
not fit together** — if egress works for the other images, a single image failing points somewhere else,
and verification disproves the claim outright:

```
$ docker manifest inspect docker.io/grafana/grafana:13.2.1-distroless
  ... valid manifest list ...
$ docker pull docker.io/grafana/grafana:13.2.1-distroless
  Status: Downloaded newer image for grafana/grafana:13.2.1-distroless
```

The image exists and pulls on retry. **No product issue follows (#1371 is not warranted)** — the
reference in Sol's values is valid.

The cause of the original error was lost: the import loop redirected each pull's output to `/dev/null`,
so "pull failed" was recorded without its reason. That is how an unverified assumption became a written
claim in this report — the same failure mode this thread has been correcting elsewhere, here in the
run report itself. The fix when re-running: never discard a failing command's output, even in a loop.

### Disposition

The cluster (`k3d-sol-local`) and the generated workspace (`dogfood_2026_10_10`) were **removed** — the
substrate cannot reach a working state in this environment, so leaving them running would only cost
resources.

### Which verification can be a gate

**Local verification cannot gate this work while it cannot run in the primary development environment.**
The golden path here reached neither a running service nor a database, so anything depending on a live
local substrate is unverifiable on this machine. **Cloud verification is the gate** — and the
resource-bindings model's "same resolved bindings across runtimes" claim is what makes that acceptable:
one source of truth is exactly what lets a change be verified on one path and trusted on the other.

### Consequence for the run

Steps 4–9 remain unreached: no `sol migrate`, no `/health`, no `POST /charges`, no notification row, and
the two-minute claim is still unmeasured. **The local substrate is currently not verifiable in this
environment**, which matters beyond the dogfood run: it is also the substrate 2c would use for local
verification. See the run's follow-up note in #1367.
